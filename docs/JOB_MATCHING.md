# 第四阶段岗位智能匹配

## 操作流程

打开岗位匹配，粘贴或导入 JD，保存岗位。点击「解析 JD」会先显示脱敏文本和模型主机。提交后观察任务进度，核对职责及要求，可修改技能名称或要求重要性。确认要求后选择已确认的简历版本并计算匹配。历史报告保留本次采用的 JD 和简历版本。生成求职建议时会预览由岗位要求名称和匹配状态构成的摘要。

## 解析与评分

JD 指岗位说明，通常包含职责和任职要求。job_parser.py 的 JD_PROMPT 要求模型保留引用并区分硬性、优先和加分条件。Pydantic 校验返回结构。后端丢弃无法定位的引文，识别优先、加分措辞，再由用户核对。岗位填写的来源链接作为出处保存。

job_matching_service.py 从当前用户的简历版本、能力画像和档案读取事实。技能匹配对已有能力名使用规范化名称和少量明确别名。对工作年限等复杂条件，证据不足时显示待验证。用户可单独标记尚未提供信息、暂时无证据或明确不符合。

| 维度 | 权重 |
| --- | ---: |
| 教育背景 | 10% |
| 产品能力 | 25% |
| AI 技术 | 25% |
| 编程与数据分析 | 15% |
| 项目实践 | 20% |
| 行业理解 | 5% |

- 单项分为符合程度乘证据系数。符合、部分符合和明确不符的符合程度依次为 1、0.5 和 0。已验证、自述和推断的证据系数依次为 1、0.8 和 0.5。
- 每个维度内对有结论的硬性项取平均。总体分是可评分维度按默认权重加权后的百分制分数。覆盖率是岗位涉及的维度按权重汇总的已判定比例。全无可判定项时，总体分为空。优先、加分及重要性待确认项保留在报告中。
- 产品能力已验证，SQL 为自述，两项都符合，另有 RAG 硬性要求待验证。参考分是 (25 + 15 × 0.8) ÷ 40 × 100，结果为 92.5。覆盖率为 40 ÷ 65，结果约为 61.54%。RAG 另列为待验证的硬性要求。
- 硬性冲突优先参与投递判断，包括用户明确标记的冲突和能比较的毕业年份。低覆盖或硬性要求待核对时，建议补充准备。评分规则独立保存在 app/core/job_scoring.py，历史报告保留规则版本。
- Python 计算逐项结果与优先级。模型建议使用用户确认的岗位名称和结果状态，提供简历、面试、实践项目和行动建议。其输出结构没有分数和证据状态字段。

## 数据和权限

迁移版本为 20261121_0003。新增岗位、要求版本、匹配报告、能力差距和分析任务五张表，同一个数据库 Worker 处理简历和岗位队列。任务去重由唯一键、事务和输入摘要实现。失败后可以主动重试。岗位删除与简历证据删除会处理关联报告，所有接口按当前用户限制访问。

## 复测

百炼 `deepseek-v4.1-flash` 实测完成十份合成 JD，职责提取 10/10，原文与重要性同时匹配 15/15。评分与预先手算的参考分及覆盖率 10/10 一致。抽查的三个关键情形为全无证据时留空、92.5 分伴随 61.54% 覆盖率及 RAG 待核实、毕业年份冲突时仍单独提示硬性不符。样本结果反映了当前构造的测试场景。

评测代码为 backend/tests/evaluate_job_model.py，参考数据由 backend/tests/job_cases.py 构造。合成 JD 覆盖证据强弱、缺证、加分项、毕业年份冲突和多个权重的组合。参考分可按本文公式人工复算。真实模型调用在评测时处理合成职位文本，使用真实数据前需在页面核对发送内容。

```powershell
Set-Location backend
$env:PYTHONPATH = (Get-Location).Path
& .venv/Scripts/python.exe tests/evaluate_job_model.py ../work/phase4/model-evaluation.json
```
