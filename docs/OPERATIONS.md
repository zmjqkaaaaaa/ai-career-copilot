## 运行检查

- `GET /health` 检查 API 进程响应，启动探针可使用此接口。
- `GET /ready` 通过 MySQL 读取完整 Worker 的最近心跳。两项就绪返回 200。MySQL 不可用或没有新鲜的完整 Worker 心跳返回 503。它提供运行依赖线索，单次响应不能证明每类 AI 请求都会成功。
- Worker 约每 10 秒在任务之间写心跳，默认允许 300 秒，兼顾长任务。通过 `WORKER_HEARTBEAT_MAX_AGE` 配置。停止后要等到最大心跳年龄才过期。仅运行策略或文件清理的 Worker 不计为完整 Worker。
- API 为响应提供 `X-Request-ID`。通过它关联出错请求。应用错误记录只包含 ID、状态或异常类型等元数据。Provider 额外记录调用名、提示词版本、模型、耗时和可取得的输入/输出 Token 数。原始模型请求、完整简历、用户备注及密钥不进入这些应用日志。生产代理与服务器访问日志的保留和脱敏设置仍需上线时核验。
- 任务接口继续沿用各模块既有响应。跨模块含义上，queued 表示待领、running 表示执行中、failed 表示失败、success/succeeded 表示完成，部分模块另有业务完成态。绑定版本、可重试条件及失败编码仍按模块约定，后续改动保持兼容。

## 用户主动删除账户

从「设置」进入删除表单。登录用户要填写当前密码并明确确认。浏览器请求还要通过现有 CSRF 校验。接口处理当前账号，不能传入其他账号 ID。有进行中任务时返回 409，等任务结束后可重试。

收到请求后，单一 MySQL 事务删除账号与个人资料、原简历记录、简历定向版本、岗位、投递、面试、学习、探索等关联记录，并记录待删除的文件随机存储键。已排队且尚未开始的任务随数据删除，旧的登录 Cookie 和 Bearer 都无法再识别该账号。接口返回 202 时数据库数据已经删除，实际文件清理已安排。

Worker 从 `pending_file_deletions` 读取待清理文件。文件已不存在时可直接完成。磁盘临时错误会增加重试时间，任务保留到清理成功。只需要处理清理时可以运行 `python -m app.resume_worker --maintenance-only`。这个模式只处理经账户删除操作产生的文件清理记录。

单独删除简历文件仍沿用原流程。已保存的独立投递版本作为历史记录保留。需要清除账号关联的全部派生副本时使用账户删除。数据恢复策略要处理已删除用户的历史备份，第三方模型处理的资料受其保留政策约束。备份留存、清除证明、恢复后重新应用删除请求和灾备演练是上线前的后续工作。

## 复测

开发和测试库分别运行 `alembic current` 与 `alembic check`。在独立测试库将 `APP_ENV=test`、`DB_NAME=career_copilot_test` 设置后运行 `pytest -q tests/test_operations.py`。启用浏览器时同时启动指向测试库的 API，并在白名单中提供测试前端地址，将 `CAREER_OPERATIONS_BROWSER` 指向该 URL。

验证目标包括正常/失联/过期心跳、限流、账户二次确认、正在处理任务拦截、数据归属、事务删除、磁盘故障重试、学习上传体积限制和错误追踪。

Sprint 5 已补充共享限流、并行 Worker、模型用量和成本汇总。配置、实测与上线边界见 [性能与安全报告](PERFORMANCE_SECURITY.md)。
