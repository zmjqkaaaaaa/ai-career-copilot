# 核心代码参考答案

先完成 [题册](CODE_EXERCISES.md)，再按编号核对。代码修改题给出实现要点与测试方式。

## M01 用户认证

### 基础知识（01–05）

- **M01-01** 哈希用于校验提交的口令，经盐化和计算后生成摘要，不设计恢复明文；加密可以用密钥解密。
- **M01-02** 验证签发数据未被篡改及其来源；载荷可解码，不能存放密码。
- **M01-03** 阻止页面 JavaScript 直接读取 Cookie，浏览器仍按规则携带它。
- **M01-04** 401 表示未通过会话认证。已登录去读他人记录，业务按归属限定，可返回 404 或权限拒绝。
- **M01-05** 同一时刻可能有两个注册事务，应用预查询无法替代数据库唯一约束。

### 代码理解（06–10）

- **M01-06** 统一大小写规范，与 authenticate 中的邮箱比较一致。
- **M01-07** flush 把变更发给数据库，便于取得 ID、触发约束；commit 提交事务。
- **M01-08** 仍做一次口令哈希验证，减小有无用户校验路径的耗时差异。
- **M01-09** 检测到 Authorization 就走 Bearer 和 api audience。头无有效令牌时不会转去 Cookie。
- **M01-10** 浏览器携带 HttpOnly Cookie 请求 users/me，current_user 按 browser audience 验证并查询账号。

### 项目场景（11–13）

- **M01-11** 用两个合成账号，一个创建档案或报告，另一个用已登录会话读其 ID，断言失败且其自身列表无该条。
- **M01-12** current_user 额外查询 User 并拒绝非活动账号。
- **M01-13** 最多一个成功。另一个数据库唯一冲突，回滚后按现有实现转为 EMAIL_EXISTS。

### 代码修改（14–15）

- **M01-14** 声明 CurrentUser，查询同时筛当前 user.id 和记录 ID。以非本人和匿名验证边界；不接受用户传入的所有者当授权。
- **M01-15** 先建一个合成账号，再注册同邮箱不同大小写。断言 409 和 EMAIL_EXISTS，同时确认第一账户仍可登录。

## M02 文件上传

### 基础知识（01–05）

- **M02-01** HTTP 请求的文件部分，与普通表单字段区分；后端参数名决定匹配哪一部分。
- **M02-02** 扩展名由文件名控制，需结合签名和 DOCX 包结构。
- **M02-03** 分块读取和累计大小，不一次把文件全部加载为字节串。
- **M02-04** 服务端生成的标识，用来定位原件，和用户可见的文件名独立。
- **M02-05** 前者有可抽取字符；仅图片的 PDF 需要 OCR，当前解析器未做 OCR。

### 代码理解（06–10）

- **M02-06** 读取一块并赋值，空字节时自然退出，循环内可以累计并限制大小。
- **M02-07** 排他创建二进制文件；若路径已存在则拒绝覆盖。
- **M02-08** 恢复流位置，后续解析从开头读取。
- **M02-09** number、location、text，分别标识顺序、出处和文本。
- **M02-10** 本地 parse、preview 之后，用户确认并 POST extract 触发外发任务。

### 项目场景（11–13）

- **M02-11** 在临时存储提交合成超限文件，断言 413、没有遗留原件且未创建可用简历记录。
- **M02-12** 显示无可提取文字的原因，提示上传含文本层 PDF 或 DOCX。
- **M02-13** 只保留最后名称用于显示，落盘路径以服务端随机键定位。

### 代码修改（14–15）

- **M02-14** 构造扩展名为 .pdf 且无 PDF 签名的无害测试字节，断言 415 与清理完成。
- **M02-15** 在现有任务错误反馈按错误码提示更换有文本层文件，保留上传入口；以固定失败响应验证文案和恢复路径。

## M03 LLM 接入

### 基础知识（01–05）

- **M03-01** 分别用于认证、选择服务地址、指定模型。
- **M03-02** 浏览器代码和网络请求对用户可见，后端可隔离凭据及控制用量。
- **M03-03** 系统放任务约束、示例和 Schema；用户消息携带待处理 JSON。
- **M03-04** 不能。分词与语言、模型相关，以提供方用量或相应分词统计为准。
- **M03-05** 任务重试受用户、业务状态和次数约束；SDK 可在调用层重复发送，当前 Provider 禁用后者。

### 代码理解（06–10）

- **M03-06** 从 SecretStr 的值构建 OpenAI 客户端；前端请求无需该密钥。
- **M03-07** 防止超大输入和不受控开销，且给用户可修正的错误。
- **M03-08** 识别会影响处理的模型、接口和输出配置，避免任务在确认后静默换处理条件。
- **M03-09** 该次调用返回或抛出异常时都执行，记录状态耗时和有则提供的用量。
- **M03-10** Provider 抛出 MODEL_RATE_LIMIT，HTTP 包装为业务的上游失败；前端按任务反馈，不应混同为本产品限流。

### 项目场景（11–13）

- **M03-11** 终止旧确认任务，刷新显示新地址与材料，用户重新确认后按模块规则发送。
- **M03-12** 任务可记录模型输出不完整，保留已有可用版本；本次结果还不能作为业务事实。
- **M03-13** 标记缺失并报告覆盖率，成本不填零；有用量且有配置单价才估算。

### 代码修改（14–15）

- **M03-14** 替换客户端为可抛拟真 APIStatusError 的测试替身，断言 MODEL_RATE_LIMIT 并检查只调用一次及未落可用结果。
- **M03-15** 在错误映射或页面任务反馈层提示可重试，保留任务 ID 和状态。先用固定样例验证重试不会产生重复可用结果。

## M04 结构化输出

### 基础知识（01–05）

- **M04-01** JSON 是数据格式，Schema 描述字段契约，Pydantic 在 Python 中执行验证并构造对象。
- **M04-02** 字段可能缺失、类型不符或枚举非法。
- **M04-03** 不一定，类型与原文证据是两类校验。
- **M04-04** 对象模式约束返回 JSON 对象；Schema 模式将字段规范也交给服务方；本地始终验证。
- **M04-05** null 表示未知或缺测，负面结论需编码为独立状态或有明确依据。

### 代码理解（06–10）

- **M04-06** 无选择项、截断或没有内容时。
- **M04-07** 捕获 ValidationError，映射 MODEL_OUTPUT_INVALID。
- **M04-08** 将大小写与空白规范化，然后做子串存在检查。
- **M04-09** 对无效原句报 422；使用用户编辑的优先级，保留通用去重比较。
- **M04-10** 如果模型给出且原文里找不到，就将字段置为 None。

### 项目场景（11–13）

- **M04-11** Prompt 约束与领域规则可拦明显错误，用户核对要求或人工评测处理语义歧义。
- **M04-12** 该引文不在当前 JD，用户编辑路径拒绝，模型抽取路径跳过该项。
- **M04-13** 检查原始响应、Pydantic 模型配置和契约版本，再看是否需迁移下游，避免绕开校验。

### 代码修改（14–15）

- **M04-14** 构造形状正确的 Requirement 与不含该引文的 JD；分别断言解析时移除、编辑时返回 JOB_EVIDENCE_INVALID。
- **M04-15** 先决定是否可空和兼容默认，更新相应 Schema、Prompt 示例与版本、前端展示和评测，测试没有新字段的历史数据如何读取。

## M05 岗位匹配

### 基础知识（01–05）

- **M05-01** 职位说明，包含工作职责、技能及资格要求。
- **M05-02** 用 importance 表示 required 等等级，各项保留 JD 原句并允许用户核对。
- **M05-03** 匹配分看已评估硬性条目的加权结果，覆盖率关注有多少适用要求可被评分。
- **M05-04** 相同的确认输入、证据、参数和规则会得出可复算结果。
- **M05-05** 获取方式与可信度不同，规则保留状态并对评分使用不同权重。

### 代码理解（06–10）

- **M05-06** 保留能在原文命中的项，用保序字典去重。
- **M05-07** 不允许，按用户和 content_id 限制画像查询，显式选择不匹配时返回错误。
- **M05-08** 点数 None，被排除在评分分母之外，但若硬性适用仍降低证据覆盖率并参与风险判断。
- **M05-09** 仅经过提取、原句核对和用户确认的岗位要求中，required 项进入规则打分，职责段不直接计分。
- **M05-10** 它仍进入 hard_flags。即使计分，投递结论也需要注意这个硬性证据风险。

### 项目场景（11–13）

- **M05-11** 展示覆盖率和学历项自己的状态，分数可能只利用已知项。未知和不满足分别处理，不承诺录用。
- **M05-12** 岗位 ID、JD 要求修订及评分规则版本尽量一致，显式核对换掉的简历版本及证据。
- **M05-13** 核对原句保留两项，不把加分写成硬性。通过产品中用户确认要求后再匹配。

### 代码修改（14–15）

- **M05-14** 准备匹配技能和明确学历不符两类事实，断言硬条件在 conflicts/hard_flags；建议为先补足，不随其他分项清空。
- **M05-15** 要求两报告同属本人、同岗位和修订，标注规则是否相同。对齐要求序号或稳定键，分别展示状态、出处和覆盖变化。

## M06 GitHub 项目理解

### 基础知识（01–05）

- **M06-01** SHA 指向具体提交，仓库的 HEAD 会随推进变动。
- **M06-02** 当前入口接受公开 github.com 仓库 URL，并由服务读取限定范围。
- **M06-03** 阅读代码文件，提取导入、符号或结构而无需运行项目。
- **M06-04** 可跳到同一提交准确复核解释依据。
- **M06-05** 前者使用词项、路径和符号匹配，当前项目使用它；后者通常依赖嵌入与向量相似度。

### 代码理解（06–10）

- **M06-06** HTTPS、主机、仓库首页路径、格式和额外参数，归一化 owner/repo。
- **M06-07** 按文件内容和符号划窗口，路径/名字命中权重大；排序去重并限制条目数和字数。
- **M06-08** 后续文件和报告需属于同一版本，避免扫到后来更新的代码。
- **M06-09** citations 返回 CODE_FILE_NOT_LOADED，提示先读取文件。
- **M06-10** 只把有效 ID 和能核实的引文转为对应代码引用；符合格式不代表引文可信。

### 项目场景（11–13）

- **M06-11** 核对请求的仓库和 commit，以及讲解绑定的 snapshot_id 和外链 SHA，优先打开原提交。
- **M06-12** 检查 HTTPS 首页、可见性、上游限流、仓库/文件大小和任务错误码；合成测试可重现限流。
- **M06-13** 能说明配置声明了依赖或入口，实际运行需要独立验证，继续引用其他文件。

### 代码修改（14–15）

- **M06-14** 构造两个合成 ProjectFile，分别给同名函数；使用 file_id 限定并断言引用文件及行范围。
- **M06-15** 用已选 commit、可信仓库标识与已验证路径行号组装链接；测试同名文件、分支变化和无证据时的界面行为。

## M07 模拟面试

### 基础知识（01–05）

- **M07-01** 保存设置、版本、周期与来源的一次训练实体。
- **M07-02** 应用存储题目、答案和状态，下一轮重新组织所需上下文。
- **M07-03** 追问可关联父题并基于当前回答；新题由阶段推进决定。
- **M07-04** 分数以符合条件的回答加权；覆盖不足时不输出分数，并说明未评范围。
- **M07-05** 按一致口径定义评价维度和参考标准的评分表。

### 代码理解（06–10）

- **M07-06** 避免晚到或过时的处理结果覆盖已更改状态。
- **M07-07** 确保追问依据来自已提交的回答，而非模型虚构。
- **M07-08** 根据时间检查结束会话，并按已回答内容保存报告，未覆盖阶段仍标记。
- **M07-09** 支持同会话重复读/结束，避免多次生成同一报告。
- **M07-10** 内连接只保留题与答均存在的记录；未评阶段从计划和已答范围区别计算。

### 项目场景（11–13）

- **M07-11** 后端限制阶段时间、题数并拒绝追问的子题再次产生追问；需要用合成测试检查触发分支。
- **M07-12** 预览和任务绑定会话修订，后端核对存量任务、题号和状态；前端也能在提交时禁用动作。
- **M07-13** 展示已答反馈和未评估阶段。分数缺失时表达证据不足，勿用零分替代未知。

### 代码修改（14–15）

- **M07-14** 构造合法结构、错误引文和确定的阶段设置。断言不新增追问，验证合理推进或当前业务失败分支。
- **M07-15** 从本次计划/实际生成题与已答题取数据并定义口径；测试零作答、早结束及含动态追问；不影响既有评分。

## M08 数据库

### 基础知识（01–05）

- **M08-01** 主键标识本表一行，外键约束关联记录存在和删除行为。
- **M08-02** ORM 把表映射为对象，执行时仍生成 SQL；复杂查询要理解所产生的语句。
- **M08-03** 报告与差距等关联更新可以一起提交或回滚，避免不完整状态。
- **M08-04** 多个列按一定顺序在同一索引中，能提高与该顺序匹配的筛选及排序。
- **M08-05** 前者管理版本化的数据库结构迁移；后者管理运行时查询、对象和事务。

### 代码理解（06–10）

- **M08-06** 一个条件隔离用户，另一个限定业务对象；同 JD 修订条件保证报告对应当前来源。
- **M08-07** 验证指定报告的版本、岗位和可选简历，避免默默选错来源。
- **M08-08** InterviewQuestion.id；额外限制当前会话，按 ordinal 排序。
- **M08-09** 先取得数据库产生的报告主键，供差距外键使用，两步仍在同一事务。
- **M08-10** 前缀 user_id 等值筛选，后续 id 支持排序和快速定位，实际执行计划需验证。

### 项目场景（11–13）

- **M08-11** 检查权限、连接条件与历史数据。用隔离副本定位，补跨用户或跨版本回归测试。
- **M08-12** 按差距重复报告。明确每行粒度，用聚合或 COUNT(DISTINCT report_id) 得报告数。
- **M08-13** 决定可空/默认及数据回填，写版本迁移，在隔离库验证新旧版本和数据保留。

### 代码修改（14–15）

- **M08-14** SELECT user_id, job_id, COUNT(*) AS matches FROM job_matches GROUP BY user_id, job_id。用户页面还要用参数限定当前用户。
- **M08-15** 以 job_positions 开始，LEFT JOIN job_matches，连接中限制相同岗位、用户和 revision；WHERE 限定岗位用户和 confirmed，再按岗位分组，COUNT(m.id) 得 0。
