# 从试用反馈到产品迭代：作品集、档案与岗位匹配

项目负责人邀请两位有设计背景、希望转向 AI 产品的朋友试用，发现作品集也是他们提交项目经历的主要形式。本轮还收集到关于档案重复填写、经历证据和评分解释的反馈。反馈由项目负责人转述，参与者的个人材料和原始截图未纳入公开案例。

## 反馈如何改变了产品

| 用户遇到的问题 | 产品决策与理由 | 本地验证 |
| --- | --- | --- |
| 设计方向的候选人主要通过作品集描述实践 | 在同一入口接收带文字层的 PDF 或 DOCX 作品集。项目背景、过程和个人贡献沿用原文证据及版本机制，降低用户重新整理材料的成本。 | 两份合成作品集均通过上传、解析、确认和匹配。PDF 可定位到引用所在页。 |
| 上传后任务停在队列，后台恢复后才发现文件超过页数限制 | 启动器同时核对进程与心跳，并在入口提前说明 PDF 最多 20 页。 | 停止任务进程后重新启动成功；再次启动复用了同一进程。 |
| 项目里写了具体能力，报告仍让人感觉全部未验证 | 将能对应 JD 的具体行动标为「简历原文支持」，同时展示来源。资历要求、间接背景和仅有计划的内容分别处理。用户能看懂现有经历已经覆盖什么。 | 合成材料中的 Prompt 设计和评测为基础要求提供原文证据；「计划使用 SQL」未计为实践。 |
| 简历解析完还要手填个人档案 | 跨页面复用最近确认材料，自动预填可识别的空白字段。保留已有值，用户核对后一次保存。 | 合成账号验证了确认前后档案草稿的返回结果、字段映射及账号隔离。 |
| 简历已写明起止年份，JD 仍要求核实在读 | 当前年份位于明确的学习区间内时，将该教育经历作为在读依据。全日制等附加条件需要自己的原文依据。 | 对照合成的当前在读、毕业年份已到、缺少全日制说明三个情况，核对分数和原文引用。 |
| 无硬性要求的维度也应有匹配结果 | 以硬性要求为基准，优先条件、加分项和重要性待确认项按 50%、25% 和 12.5% 计入。只有非硬性条件时标为参考匹配分。 | 合成用例覆盖只有非硬性条件、两类条件混合、有硬性冲突和全部缺证的情况。 |

## 面试时可演示的例子

旧版截图中，唯一计分的硬性项是「本科及以上学历在读」。旧规则没有认出起止年份，导致报告为 0 分。截图未展示其他条目的逐项结果，因此无法用总分判断这位试用者的全部能力。

用合成材料复现两种情况。对于「本科及以上学历在读」，合成简历记录了覆盖评估年份的硕士阶段，规则返回「简历原文支持」。对于只有「Python 优先」「PRD 加分」和一项重要性待确认条件的 JD，合成简历对 Python 有明确自述，报告给出 35.56 的参考匹配分和 44.44% 的证据覆盖率。两项示例使用各自独立的测试材料，可通过对应测试复查。[岗位匹配测试](../../backend/tests/test_jobs.py)

## 验证与下一步

本轮隔离后端回归为 132 项通过、19 项跳过，前端构建通过。作品集支持可提取的文字层，在线链接和主要靠图片表达的内容尚未纳入读取。真实试用者对新版的复测待记录，当前应观察他们能否用同一 JD 重新匹配、定位证据、说明分数含义并核对预填字段。[计分规则](../JOB_MATCHING.md) · [简历与作品集解析](../RESUME_AI.md) · [首轮试用](USER_TRIAL_RECAP.md)
