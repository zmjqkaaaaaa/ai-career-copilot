# AI Career Copilot 产品案例

**设计问题**　求职者拿到一份 AI 产品经理实习 JD 时，怎样找到投递前最值得处理的一项差距，并证明自己真的补上了证据？

## 1. 项目背景与用户证据

我在准备 AI 产品方向实习时多次投递没有收到进展。没有相关实习，原有无人机项目可以说明我使用 AI Coding 做出了东西，但作品里很难直接体现需求拆解、产品取舍和用户判断。我也曾在牛客和小红书上对照其他人的简历，项目和经历不同，模板只能解决一部分表达问题。与身边一位有多段实习经历的同学交流后发现，他在投 AI 产品岗位时也曾卡在一面。这个个案促使我把问题范围从简历表达延伸到项目和面试准备。

| 证据 | 能支持什么 | 仍需验证 |
| --- | --- | --- |
| 本人求职复盘 | 在实际准备中遇到证据不匹配和差距优先级不清 | 这种情况在其他用户中出现的频率 |
| 一位同学的个案 | 有实习经历的人也可能卡在面试环节 | 面试受挫的具体原因，产品是否能改善 |
| 合成账号的端到端验收 | 多模块能共享资料和版本，组织一次完整的准备任务 | 真实用户能否独立完成，是否愿意持续使用 |

首要用户是做过一些项目并学过相关知识、正在投 AI 产品实习但缺少对口经历的学生。零基础入行者、已经有项目需要面试复述的人可以使用各自入口。其动机与优先级仍是假设。 [PRD 用户研究](PRD.md) · [真人试用方案](../USER_VALIDATION.md)

## 2. 竞品分析与定位

采用公开页面走查，以“已有简历和一个意向岗位”为同一任务。记录能看到的输入、对照输出和版本机制。用公开说明判断能力范围，实际账号输出及推荐质量未做统一实测。

| 参考方案 | 公开能力 | 可借鉴之处 |
| --- | --- | --- |
| MatchCV | JD 必备、加分项拆解及定向内容改写 | 让首次诊断的要求分层更易扫读。 [MatchCV](https://www.matchcv.cn/zh-cn) |
| Jobscan | 简历对照 JD、报告和 ATS 优化教程 | 从同一目标岗位的复查体验学习版本对照。 [Jobscan](https://www.jobscan.co/jobscan-tutorial) |
| Teal | 对照 JD 的匹配分、关键词和简历跟踪工具 | 让建议能落在已有经历的条目上。 [Teal](https://www.tealhq.com/tool/resume-job-description-match) |
| 社区范例和人工请教 | 本人曾通过牛客、小红书比较他人简历 | 学习写法的门槛低，仍要自行判断个人经历是否构成岗位证据。 |

定位高度聚焦于 AI 产品方向初期求职。差异化假设是把一项优先差距追溯到原句和个人证据，按照差距性质提供真实改写、项目练习或面试复练。是否优于其他产品的结果需要任务对照。 [PRD 市场分析](PRD.md)

## 3. 产品设计与取舍

最小任务路径是“确认简历与 JD、查看优先差距、修改一处真实经历、用同一 JD 复查”。记录原始报告和两份输入版本，让用户能解释证据是怎么变的。若缺的是能力本身，可转向项目或学习，不要求用措辞掩盖缺口。项目 PRD、Git 提交、投递版本与面试资料可保存来源，使下游能回到相同上下文。

| 关键决策 | 解决的问题 | 与真实实现的对应 |
| --- | --- | --- |
| 匹配结果按证据组织 | 用户需要知道分值为何可信、哪项差距该先处理 | 显示 JD 引文、简历依据、证据类别、覆盖率和优先级 |
| 同一 JD 支持复查 | 修改后希望看清有什么变化 | 用新版简历生成匹配、分别打开历史报告；逐项并排对照仍属后续设计 |
| 把缺口转为行动 | 完成诊断后仍需要练习或投递 | 探索会话关联报告，项目可关联公开仓库，面试薄弱项可进入学习路线 |
| 按版本保留面试输入 | 从投递去训练时找回实际使用的资料 | 关联简历、JD、投递或代码提交快照，外部招聘渠道由用户自行操作 |

## 4. AI 技术方案

LLM 处理写法各异的 JD、简历、对话和代码说明。主要能力是抽取、归纳、提问、解释和建议。Python 负责身份、任务、证据、版本、匹配评分、阶段推进与持久化。以 JD 为例，模型先提出逐项要求，程序检查原文，用户确认后由规则计算分值和覆盖率。代码解释按固定 Git SHA 选片段。面试根据已答内容拟议追问，并由代码核对时间、轮次和引用。

Prompt 使用版本化指令、示例、输出契约和已核对材料。防止无依据结论依赖多层设计：外发前核对范围、本地 Pydantic 校验、引用核对、确认与保留未知状态。有效引用的存在不能证明解释正确，质量评测另检查证据是否真的支持结论。项目当前采用固定工作流及代码证据检索。 [AI 工作流](AI_WORKFLOW.md) · [Provider 源码](../../backend/app/ai/provider.py)

## 5. 质量验证与产品指标

| 维度 | 结果或口径 |
| --- | --- |
| 系统联通 | 历史隔离使用 MySQL 8.4、Edge、合成账号和受控 AI 响应。全量回归记录 120 通过、10 跳过。验收确认报告与来源能跨模块传递，跨账号访问被限制。 |
| 真实模型业务质量 | 历史阿里云百炼合成基线 12 条，12/12 结构通过，9/12 业务通过；需复核简历解析分类、保守改写和面试评分。 |
| 离线评测 | 最近重放 12/12 正例通过，12/12 内容错误被识别、12/12 损坏响应被拒绝。这反映评测规则行为。 |
| 产品核心指标 | 分母是首次读完匹配报告、至少有一项差距可通过简历表达改善、且观察窗口结束的试用者。分子是 48 小时内改完一处真实经历、用同一 JD 复查且能解释证据变化的人数。尚无真实观测。 |
| 过程信号 | 用户能否独立指出优先差距、找到原文或证据、完成修订和回到同一 JD；按阻塞发生点记录，独立完成与接受提示分开统计。 |

## 6. 当前限制与迭代

1. **优先验证诊断是否促成行动。** 用合成资料预演，从真实目标用户的小样本观察 48 小时任务。先报告人数、阻塞点及是否需要提示，再讨论比例。
2. **针对阻塞点做最小改动。** 如果用户说不清优先差距，比较按紧迫度引导与现有标签。如果找不到修改前后的证据变化，优先设计同 JD 的逐项对照。
3. **扩大关键 AI 场景的样本。** 拆开事实召回与分类、保守改写的可信度与可采用性，补齐概念题和实现题的评分区别。
4. **复验环境能力。** 真 GitHub 配额、可选 Tavily、模型在线稳定性和生产部署各有独立条件。上线或谈真实影响前分别验证。 [部署与验证范围](../DEPLOYMENT.md)

## 7. 个人贡献

我发起项目并提供自己的真实求职经历。作为项目负责人，我明确了 AI 产品实习的目标用户，选择“从职业画像和 JD 分析看出差距”的入口，确定差距按紧迫度组织，并给出改一处真实经历、48 小时内用同一 JD 复查的验证目标。我通过 Codex 协作推动分阶段实现和复盘。实现代码由 Codex 辅助完成，技术与测试成果以仓库、文档和执行记录为准。
